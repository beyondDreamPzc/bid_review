> 版本说明：本文正文保留0.8及以前的实现记录。1.0已新增混合检索/重排、DOCX和辅助检查等，当前状态与限制以[1.0交付说明](版本1.0交付记录.md)及[完整启动与运维](完整启动与运维.md)为准；新增能力尚待运行验收。

本文描述当前代码，RAG、Milvus及LangGraph自动审查未实现。

## 领域对象为什么分开

- Document 是逻辑文件；DocumentRevision 是具体字节；ParseArtifact 绑定修订和解析配置；DocumentBlock 提供原文定位。
- Requirement 是长期身份；RequirementRevision 正文及来源不覆盖，确认后进入 BaselineItem。
- Baseline 冻结完整要求；MaterialSet.items 冻结文件修订、hash、解析配置与正式/参考角色。
- ReviewIssue 保存登记时的差异事实；唯一 WorkItem 承载整改状态。新文件不改写旧问题。
- TaskSubmission 与 TaskDecision 追加每次整改和复核，不能只更新“完成”字段。
- RequirementDecision 单独记录逐项审核，避免未检查却没有问题的要求被算作完成。

Project.current 指针、WorkItem.current_submission 指针由应用事务内维护，不建反向外键以避免表间依赖成环。核心事实有外键，但 JSON 内的证据/材料成员关系仍由业务服务校验，不能绕过服务直接写业务表。

## 写入一致性与权限

business.mutate 先结束认证读取事务并使已有 ORM 缓存过期，再 SELECT Project FOR UPDATE，随后读取成员、幂等记录和业务状态。这样在 MySQL 默认 REPEATABLE READ 下，不会先建立旧快照，等待锁后仍读锁前的数据，也不会复用调用者预读的旧任务对象。所有业务写入遵循同一项目锁顺序。

## 引导演示的边界

FastAPI 托管原生 HTML/CSS/JS，无额外前端构建步骤。DemoWorkspace 保存随机 Cookie 的摘要、隔离项目与三个演示人物的 ID、七天有效期。浏览器不拿到正式 API Key；演示适配层只接受当前 Cookie 项目的动作，不能传入任意项目 ID，原件下载同样校验归属。写请求检查同源 Origin，Cookie 为 HttpOnly/SameSite=Strict，所有源文件明确标记构造样本。

演示默认只在本机 Compose 启用，普通 Settings 默认关闭。样例准备、修订保存、基线、材料快照、整改与复核复用既有服务。提交前先在项目锁内检查任务/材料版本，再依次幂等上传、解析、发布和提交，网络重试沿用各阶段派生键。过程若中断，可能已有新文件但未完成提交；不会伪装已复核，可以刷新并用同一请求继续。

首版不包含模型推理：疑似冲突预设为2小时/4小时，页面提示属于样例数字规则，最终满足由用户明确确认。演示不是实际组织身份登录，也不是任意真实文件的生产管理界面。

锁内校验角色、请求 hash、expected_epoch、要求修订或任务 version；一次提交事实、审计和幂等响应。相同用户/项目/动作/键的同请求返回原响应，异请求返回409。幂等重放也提交释放锁。单项目写入串行化，适合当前人工协作规模，不宣称高并发写入能力。

API Key 只保存 SHA-256 摘要。对象访问按项目成员隔离，无权限/不存在统一404；EDITOR 不能确认要求或复核；提交人不能复核自己提交的整改；成员权限在项目锁内重新读取。

## 旧结论怎样失效

review_epoch 随基线/材料发布递增。提交和最终审核保存当时基线、材料、epoch；与当前不一致，旧提交/验收显示 NEEDS_RECHECK，旧最终审核不计覆盖率。

同一要求的 review_version 在新增问题时递增，审核记录当时代次。同一 epoch 新发现问题也会使之前“满足”失效，验收后仍须最终确认。

比较最新要求集合与当前基线集合，识别未发布修改。pending_requirement_changes 为 true 时不能显示完成。首版无要求退休/删除，基线必须包含全部最新已确认要求。

## 状态与报告

任务：TODO → IN_PROGRESS → SUBMITTED → ACCEPTED；退回走 RETURNED → IN_PROGRESS。已提交/已验收的输入过期后，可以 START 再提交。只有任务负责人可开始/提交。

报告逐项核对当前基线：有未解决问题为 ISSUES_OPEN；没有当前审核为 UNREVIEWED；曾确认有问题、问题处理后仍待最终确认时为 NEEDS_REVIEW；有当前满足/不适用决定且无未解决问题为 REVIEWED。

输入齐备、要求数大于0、全部 REVIEWED、无未解决问题且无未发布修改，manual_review_complete 才为 true。该字段是人工工作流状态，不是自动采购合规判断。

## 解析任务可靠性

上传事务同时登记 revision、job、outbox。Redis 是投递通道，MySQL 是事实源。Worker 租约领取，递增 lease_token 拒绝旧执行者提交；恢复扫描重新投递过期任务与丢失消息。revision/profile 唯一约束避免重复产物。

当前新任务使用MinerU，历史探针继续兼容。所有产物固定NEEDS_REVIEW，模型要求抽取是独立后续任务。新配置新建profile/产物，不覆盖引用。

## 验证与后续

0.5.0 在原 `pdfplumber-probe-v1` 的冻结 JSON 上运行独立 `text-quality-v1` 诊断，不重解析、不改原 block_id、正文或坐标。读取先验证 JSON 的 SHA-256 与已登记产物摘要，再逐页统计字符和可解释规则；无文字不能推断一定是扫描页，规则也不能证明没有漏字、表格语义正确或多栏顺序正确。

PageQualityReview 以 artifact/page/version 唯一约束追加历史。共用项目行锁、幂等和权限入口，expected_version 防止覆盖别人意见，所见诊断规则版本变化要求重看。记录绑定不可变产物，新文件修订或新解析配置不继承旧决定；质量核对不增加业务 epoch、不修改基线或最终人工结论。人工业务不设此门槛，0.6.0 的模型抽取须选页最新意见为 TEXT_USABLE。规则警示、人工核对进度和人工需处理页数分别统计，人工确认空白不会删除原规则提示。

`scripts/evaluate_extraction.py` 从可配置清单验证指定页码短句和页数，默认4份同模板构造样本、6个检查点。输出仅带命中结果与来源摘要，不复制检查点原文，默认在排除 Git 的 data/evaluation；不能把该命中率当作整文准确率。质量 API 与构造并发集成验证见 [解析质量验收](quality-verification.md)。

0.4.0 增加 `/workspace` 的实际账号网页，与 `/` 构造演示分开。WebSession 只存随机会话令牌的 SHA-256 摘要；七天有效、退出撤销，Cookie 为 HttpOnly/SameSite=Strict，HTTPS 时设置 Secure。登录及退出要求同源 Origin；Cookie 认证写操作由共用依赖检查 Origin。显式无效 X-API-Key 不回退到 Cookie；原有 API Key 客户端保持兼容。登录验证错误去掉被拒绝输入，避免回显密钥。未实现限流和组织 SSO，当前仅本地端口使用。

工作台聚合接口在一个读取事务内返回项目文件/修订/任务进度、最新要求、冻结基线、正式材料、问题任务、成员和报告。MySQL REPEATABLE READ 提供同一读取快照；SQLite 用于功能测试，不据此宣称并发一致性。当前规模小且无分页，存在逐条查询；大量项目需后续改为分页、批量装载和增量刷新。

网页写入复用既有业务接口和权限检查；创建项目新增可选幂等键，通过用户行锁避免网络重试新建两个项目。文件解析进度轮询仅更新文件列表和未编辑的材料选择，不清空未保存表单。引用选择跨页保留，服务端仍回查所有出处；前端不接收自造 quote。选择文件修订并发布材料集是显式步骤，上传不偷偷改变审查输入。

真实网页没有演示角色切换。成员查找仅 OWNER 可用，只返回已有用户的姓名/ID并排除构造演示人物；账号仍由 CLI 配置。Markdown 报告从当前事实与有效决定生成，包含来源和原件摘要，用户文本转义防止插入 HTML 或链接。网页文档见 [真实项目工作台](真实项目工作台.md)。

SQLite 测试验证权限和业务不变量；真实 Compose 验证 MySQL 迁移、并发幂等、Redis/Worker。历史见 [0.4.0 工作台实测](workspace-verification.md)。0.6.0 新增模型候选抽取，后续准备多模板标注样本、真实模型效果评测和 Milvus 检索。模型不直接发布基线、验收整改或作最终决定。

## 0.6.0 候选抽取怎样接入现有业务

ExtractionRun 固定解析产物、页级意见 ID、来源快照、模型非敏感配置、提示词版本与批次结果。RequirementCandidate 分开保存不可变原建议、服务端出处、状态和一次人工处理凭据。采纳调用已有 create_requirement，因此仍生成 DRAFT，不改变基线或 epoch。

创建任务共用项目锁与幂等事务，Job/outbox 同时提交；dispatcher 按 kind 投递 extract 队列。独立 extraction-worker 逐批调用 HTTP 服务，网络期间不持有数据库写锁。成功批次保存检查点，最后按项目→任务顺序加锁，重新验证输入与 lease_token，全部完成才发布候选。复用原有恢复扫描，AI 任务失败不会把成功解析的 PDF 改成 PARSE_FAILED。

取消提升租约令牌，旧执行者不能落库；重试保留完成批次。任一所选页的最新意见变化或同一逻辑文件上传新版，旧候选即过期；采纳时重新验证原文摘要与索引，完全相同正文和出处的要求不能重复导入。结构和出处校验无法证明语义正确，最终仍须人核对。

当前使用显式 Python 状态机，未引入 LangGraph；没有为了使用技术栈而再加一层编排。模型默认关闭，本轮仅完成合成 HTTP 契约和工作流验收。配置、限制和结果见 [候选抽取说明](AI要求候选抽取.md) 与 [0.6.0 验收](extraction-verification.md)。

## 0.7.0 MinerU解析隔离与重解析

新解析任务kind为PDF_PARSE，保留PDF_TEXT_PROBE历史种类；工作台及上传去重只查询解析种类，不混入要求抽取任务。原件及产物唯一约束保持不变，无数据库结构迁移。相同revision/profile只创建一个任务，追加重解析与outbox共用项目锁及幂等事务。

独立parse Worker镜像在/opt/mineru安装完整锁定的SDK环境，通过子进程运行推理；主进程预检原件、定期续租并验证MiddleJson完整页覆盖和坐标后提交。超时/租约失效停止进程组，避免OCR渲染进程继续工作。源码及配置详见[MinerU解析重构](MinerU解析重构.md)，本轮验证见[0.7.0验收](mineru-verification.md)。
