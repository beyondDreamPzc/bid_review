# 0.3.0：先体验，再决定方向

入口：[本机演示工作台](http://127.0.0.1:18080/)。Docker Compose 已启动时直接打开；没有启动则按 README 操作。

你在例子中是参加投标的服务商。采购方用招标文件提出要求，你用技术响应书说明准备怎样提供服务。系统让团队逐项对照，找到承诺不一致的地方，交给人修改并保留确认依据。

## 推荐体验路线

1. 开始这次文件检查。样例包含响应时限、操作培训、驻场工程师3项要求。
2. 第一项看到采购方要求2小时，而技术响应书为4小时。点“看原文”看PDF实际第2页，或打开真实PDF原件。
3. 审查人林悦登记问题并指派陈工，写清哪里要改。
4. 切到编写人陈工，开始整改，将4小时改为2小时并提交。系统保存真实修订、采用该版本、保留整改说明。
5. 切到林悦，看到改后的2小时，验收并确认这一项满足。若仍写4小时，演示会提示退回修改。
6. 报告中还有2项未检查。先阅读原文，勾选并确认，随后显示3/3，可下载检查记录。
7. 可选：模拟文件又更新一稿，观察旧完成状态失效，但历史文件和处理记录仍存在。重新提交时不会悄悄回退到旧稿。

不用配置API Key或填写接口ID。“你正在扮演”是在隔离构造样例中切换角色，不是实际账号登录。页面刷新可以继续；重新体验建立新样例，不删除旧项目。

## 已经验证的内容

- 21项自动测试覆盖旧文件工程、人工业务闭环及新增演示：角色边界、Cookie项目隔离、同源写入、中文原文/页码、阶段幂等重试、退回重做、旧版本失效和重新提交不回退。
- Linux容器测试通过，MySQL增量迁移与模型一致，原34个业务接口的规范与运行服务一致。
- 在实际本机浏览器中操作完成原文弹窗、登记问题、开始整改、保存2小时修订、另一人验收、剩余两项确认，报告显示3/3。
- 实际点击模拟文件更新，报告回到0/3并提示重新核对。
- 在600px预览宽度下检查页面操作和布局，页面无整体横向溢出；报告可在自身区域横向滚动。不声称已完成所有设备和浏览器兼容性测试。

## 这份MVP的边界

本次使用4份明确标记的构造PDF，没有真实企业资料。疑似差异是固定样例及简单数字提示，尚未接AI抽取、RAG检索或模型判断。后端记录真实保存，但界面首版仅服务这个引导案例，不具备任意真实项目的上传/台账编辑界面。

先判断“对照原文、让问题有人改、由别人复核、留住每轮依据”这个业务是否有吸引力，再决定是否投入通用前端和自动化，不需要先投入完整RAG系统。

演示开关仅在本机Compose默认启用；普通Settings默认关闭。共享部署须关闭BID_DEMO_ENABLED。Cookie只允许操作自己隔离的演示项目，无法用其访问其他项目或正式API。
