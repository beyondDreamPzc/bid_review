# 从投标业务理解接口

适用版本0.3.0，业务接口兼容0.2.0。不了解招标时先打开 [三分钟演示](http://127.0.0.1:18080/)，直接体验两份原文、指派整改和他人复核。本文供体验之后查询业务动作；字段注释在 [接口手册](API接口说明.md) 和 Swagger Schema 中。

## 用一个连续场景理解系统

下面是人工构造的例子：一家信息化服务公司准备投标，招标要求“故障响应不得超过2小时”，编写人沿用的旧响应书却写“4小时”。负责人需要知道：差异在哪里、谁去改、改的是哪一版、谁验收，以及其他要求有没有检查。

团队有负责人甲（OWNER）、编写人乙（EDITOR）、审查人丙（REVIEWER），只看进度的同事可为 READER。

| 业务动作 | 谁操作 | 对应接口 | 解决什么问题 |
|---|---|---|---|
| 建立一次投标项目 | 甲 | `POST /api/v1/projects` | 本次投标的材料、人员和问题属于同一个空间 |
| 分配编写/审查角色 | 甲 | `POST /projects/{p}/members` | 谁能改、谁能审、问题交给谁 |
| 上传招标及响应文件 | 甲/乙 | `POST /projects/{p}/documents` | 保存不可变原件，覆盖文件不能让旧依据消失 |
| 找到2小时和4小时原文 | 任意成员 | 查 job → blocks → source | 判断能回到具体文件、页码、坐标 |
| 整理招标要求台账 | 乙 | `POST /projects/{p}/requirements` | 把长文件拆为可逐项检查的要求 |
| 确认要求录入准确 | 丙/甲 | `POST /projects/{p}/requirements/{r}/confirm` | 核对期限、适用范围和例外，避免误录 |
| 冻结本轮要求依据 | 丙/甲 | `POST /projects/{p}/baselines` | 全团队按同一套已确认要求审查 |
| 选择正式响应和附件 | 乙/甲 | `POST /projects/{p}/material-sets` | 排除模板、旧文件和参考资料干扰 |
| 登记冲突并指派乙 | 丙/甲 | `POST /projects/{p}/issues` | 问题有要求、证据、优先级和负责人 |
| 开始修改、提交整改 | 乙 | `POST /projects/{p}/tasks/{t}/transitions` | 向复核人说明改了什么，引用改后原文 |
| 验收通过或退回 | 丙/甲，且不是提交人 | `POST /projects/{p}/tasks/{t}/decisions` | 编写人自己点完成不能直接关闭问题 |
| 逐项最终审核 | 丙/甲 | `POST /projects/{p}/requirement-decisions` | 没发现问题也要记录“检查过”及依据 |
| 查看本轮覆盖报告 | 任意成员 | `GET /projects/{p}/review-report` | 区分已检查、未检查、未整改和需重审 |

表中省略的路径前缀都是 `/api/v1`。`{p}`、`{r}`、`{t}` 须替换成真实返回 ID。

```mermaid
flowchart LR
    A[保存原件并定位原文] --> B[要求录入和人工确认]
    B --> C[冻结基线和正式材料]
    C --> D[登记问题并指派负责人]
    D --> E[修改文件和提交整改]
    E --> F[另一人复核]
    F -->|退回| E
    F -->|验收| G[逐项最终确认]
    G --> H[本轮报告]
```

## 先认识 ID 与版本

| 名称 | 它是什么 | 为什么需要 |
|---|---|---|
| 文件 `document_id` | 逻辑文件身份，如技术响应书 | 多次修订属于同一文件 |
| 文件 `revision_id` | 某次上传的不可变 PDF 字节版本 | 旧证据必须指向旧原件 |
| `artifact_id` + `block_id` | 某修订解析出的某段文字 | 查询页码、坐标、原文，二者须配套 |
| `requirement_id` | 逻辑招标要求身份 | 更正后仍能关联原来的问题 |
| 要求 `revision_id` | 某条要求的一次正文修订 | 不能用新正文改写旧审核依据 |
| `baseline_id` | 本轮全部要求修订的集合 | 单条要求编辑完不代表团队切换依据 |
| `material_set_id` | 本轮正式响应/附件的确切文件集合 | 最后上传的不一定是本次正式文件 |
| `review_epoch` | 当前基线与材料组合的递增版本 | 别人换了材料时旧页面不能直接下结论 |
| 任务 `version` | 任务状态的递增版本 | 防止基于旧状态重复提交或验收 |

发布基线或材料集会增加 epoch。写之前查 `GET /projects/{p}/workspace`。新要求草稿暂不替换基线，但报告会标记 `pending_requirement_changes=true`，阻止项目显示人工审查完成。

## 第1步：建立项目与人员分工

初始密钥在本地 `.env`。Swagger 的 Authorize 只填密钥值，不加 Bearer；所有用户使用各自的 `X-API-Key`，系统不靠请求体里的姓名识别人。

账号由运维用 CLI `python -m app.cli bootstrap --name 编写人 --key-env BID_EDITOR_API_KEY` 创建。先通过受控环境变量 BID_EDITOR_API_KEY 注入随机密钥，至少24字符；在容器执行时要显式传入该变量。命令只输出用户 ID，不输出密钥。当前没有公开注册接口。

甲调用 `POST /api/v1/projects`，JSON 为 `{"name":"某信息化服务投标项目"}`，得到项目 id。乙、丙调用 `GET /api/v1/me`，把自己的用户 ID 提供给甲。甲添加乙：

```http
POST /api/v1/projects/{project_id}/members
X-API-Key: 甲的密钥
Idempotency-Key: 本次授权操作的UUID
Content-Type: application/json
```

```json
{"user_id": "乙的用户ID", "role": "EDITOR"}
```

丙的 role 为 REVIEWER。OWNER 由创建项目获得，不能通过成员接口转移。已有任务负责人须保留 EDITOR/OWNER，首版没有任务转派。`GET /members` 查看本项目角色，`GET /workspace` 看自己的角色和当前输入。

## 第2步：保存原件并找到原文

甲/乙上传招标书 `kind=TENDER`、技术响应书 `kind=RESPONSE`；证明材料用 EVIDENCE，更正用 AMENDMENT。上传接口为 multipart 文件表单，不是 JSON。

上传返回 document_id、文件 revision_id、job_id。HTTP 202 仅表示接收；查 `/jobs/{job_id}` 直到 SUCCEEDED，取得 artifact_id；再查 `/artifacts/{artifact_id}/blocks` 找到相应文字块的 block_id。

本例记录两组引用：

```json
{
  "招标来源": {"artifact_id": "招标产物ID", "block_id": "2小时原文块ID"},
  "响应来源": {"artifact_id": "响应产物ID", "block_id": "4小时原文块ID"}
}
```

`GET /artifacts/{a}/blocks/{b}/source` 返回原文、PDF 实际页码、坐标和原件下载地址。引用前回看原件，尤其是表格、扫描页和上下文。当前没有 OCR 或表格语义保证。

`formal_review_ready=false` 表示不具备自动审查能力，人工流程可以继续。引用由服务端回查，不能在请求中自造一段“证据原文”。

## 第3步：录入并确认要求

乙调用 `POST /projects/{p}/requirements`：

```json
{
  "title": "故障响应时限",
  "text": "故障响应不得超过2小时。",
  "category": "TECHNICAL",
  "priority": "MANDATORY",
  "sources": [{"artifact_id": "招标产物ID", "block_id": "2小时原文块ID"}]
}
```

priority 由人工按招标定义判断。来源只能是本项目招标/更正文件。返回 requirement_id、要求修订 revision_id、revision_no=1、status=DRAFT，以及冻结的原文/页码/hash。

丙核对无误后调用 `POST /projects/{p}/requirements/{requirement_id}/confirm`：

```json
{"expected_revision_no": 1}
```

返回 CONFIRMED。这只表示要求录对，尚未判断响应满足。EDITOR 不能确认要求。`GET /requirements` 查看各条最新修订；历史用 `/requirements/{r}/revisions`。

## 第4步：发布完整要求基线

丙查询 workspace。假设初始 epoch 为0、尚无基线，调用 `POST /projects/{p}/baselines`：

```json
{
  "name": "首次要求确认版",
  "expected_epoch": 0,
  "expected_current_baseline_id": null,
  "requirement_revision_ids": ["刚确认的要求修订ID"]
}
```

有多条要求时必须包含全部最新确认版，不能挑几条让其他要求消失。最新草稿未确认、遗漏或重复都返回409。成功后 epoch 为1，保存基线 ID。`GET /baselines` 可还原历次完整要求。

## 第5步：确定正式响应材料

乙调用 `POST /projects/{p}/material-sets`：

```json
{
  "name": "响应书整改前版",
  "expected_epoch": 1,
  "expected_current_material_set_id": null,
  "items": [{"artifact_id": "4小时响应产物ID", "submission_role": "FORMAL_RESPONSE"}]
}
```

成功后 epoch 为2。FORMAL_RESPONSE 为正式响应，FORMAL_ATTACHMENT 为正式附件，REFERENCE 仅参考。至少一份正式 RESPONSE，同一逻辑文档只能选一个版本。模板里的2小时不能证明正式响应已改好。

上传新文件不会自动替换材料集，必须显式发布。`GET /material-sets` 可追溯历次选择，包含文件修订/hash/解析配置。

## 第6步：登记问题并指派整改

丙调用 `POST /projects/{p}/issues`：

```json
{
  "expected_epoch": 2,
  "requirement_revision_id": "当前基线要求修订ID",
  "title": "响应4小时与招标2小时冲突",
  "description": "已核对两份原件，请修正响应承诺并检查全文一致性。",
  "kind": "CONFLICT",
  "severity": "HIGH",
  "assignee_id": "乙的用户ID",
  "due_date": null,
  "evidence": [{"artifact_id": "4小时响应产物ID", "block_id": "4小时原文块ID"}]
}
```

一次请求建立一条 issue 和唯一 task，任务初始 TODO、version=1。问题保存登记时的要求、基线、材料和原文；改后响应不能把这条历史冲突覆盖掉。

CONFLICT 必须有正式材料证据。缺失响应/证明可用 MISSING_RESPONSE/MISSING_EVIDENCE、证据可为空，但描述须说明核对范围。负责人只可为本项目 OWNER/EDITOR。`GET /issues` 看历史问题和当前状态，`GET /tasks` 看任务和复核意见。

## 第7步：负责人修改并提交

乙调用 `POST /projects/{p}/tasks/{task_id}/transitions`：

```json
{"action": "START", "expected_version": 1, "expected_epoch": 2}
```

任务变为 IN_PROGRESS、version=2。乙在实际文件中把4小时改为2小时，通过 `POST /documents/{document_id}/revisions` 上传新 PDF，使用原逻辑文档 ID。等待解析得到新版产物和2小时原文块。

再发布新材料集：传当前 expected_current_material_set_id，选择新版产物，epoch 变为3。随后向同一 transitions 接口提交：

```json
{
  "action": "SUBMIT",
  "expected_version": 2,
  "expected_epoch": 3,
  "note": "已修正正式响应为2小时，并检查相关章节一致性。",
  "evidence": [{"artifact_id": "新版响应产物ID", "block_id": "2小时原文块ID"}]
}
```

返回 SUBMITTED、version=3 和 current_submission.id。必须有说明和当前正式材料证据。系统核验身份与版本，人仍需判断整改是否真正解决问题。

## 第8步：由另一人验收或退回

丙回看新版原件，调用 `POST /projects/{p}/tasks/{task_id}/decisions`：

```json
{
  "expected_version": 3,
  "submission_id": "当前整改提交ID",
  "decision": "ACCEPT",
  "note": "已核对正式响应修订版，承诺为2小时，接受整改。"
}
```

通过后任务 ACCEPTED、问题 RESOLVED。未改好用 RETURN，乙再 START → SUBMIT，每次意见和提交保留。即使甲有 OWNER 权限，若是甲提交的整改，也不能由甲复核。

SUBMIT 后别人又换材料/基线时，不能继续验收旧提交，返回409。乙须重新核对当前输入，START 后再 SUBMIT。历史提交查 `GET /tasks/{t}/submissions`；任务的 decisions 包含所有退回/验收。

## 第9步：逐项最终审核，再看报告

问题解决不表示每项要求都检查过。丙调用 `POST /projects/{p}/requirement-decisions`：

```json
{
  "expected_epoch": 3,
  "requirement_revision_id": "当前要求修订ID",
  "decision": "CONFIRMED_SATISFIED",
  "note": "已逐项核对正式响应，相关问题已由另一人复核。",
  "evidence": [{"artifact_id": "新版响应产物ID", "block_id": "2小时原文块ID"}]
}
```

确认满足必须有正式材料证据且相关问题全部验收；确认有问题用 CONFIRMED_ISSUE，但要先登记可整改问题；不适用用 NOT_APPLICABLE 并解释理由。决定追加保留，GET /requirement-decisions 可看历史，不能直接把历史数量当当前完成数。

`GET /projects/{p}/review-report` 的状态含义：

| 状态 | 含义 | 下一步 |
|---|---|---|
| NOT_READY | 缺基线或正式材料 | 先明确本轮输入 |
| ISSUES_OPEN | 有未解决问题或旧验收待重核 | 继续整改和独立复核 |
| IN_REVIEW | 有要求未确认或有未发布要求修改 | 补最终决定，或发布新基线 |
| REVIEW_COMPLETE | 全部要求人工确认，无未解决问题、无待发布修改 | 记录本轮版本，进行业务提交前检查 |

manual_review_complete=true 仅表示这套输入的人工流程完成，不是自动合规保证。没有问题记录时，要求仍为 UNREVIEWED，不会直接完成。同一 epoch 中新发现问题也会使该要求此前的满足决定失效，验收后仍须重新最终确认。

## 材料或要求后来又变化

| 变化 | 怎么操作 | 对旧记录有什么影响 |
|---|---|---|
| 响应书更新 | 上传原文档新修订，解析后发布材料集 | epoch 增加，旧提交/验收为 NEEDS_RECHECK，旧最终决定不计覆盖 |
| 招标更正或录错要求 | 上传更正；POST /requirements/{r}/revisions 新建草稿；确认并发布完整基线 | 草稿不悄悄替换依据，待发布修改会阻止完成；发布后旧结论需重核 |
| 仅上传参考文件 | 按需以 REFERENCE 纳入材料集 | 不能证明正式响应满足；发布任何新快照都须重核 |
| 别人已推进任务 | 刷新任务 version | 旧 expected_version 返回409，避免重复操作 |

要求修改请求体与首次录入相同，另带 `expected_revision_no`。当前采用保守策略：新基线/材料集使本项目旧结论整体过期，暂未实现自动局部影响分析、任务转派、问题撤销、要求删除。

## 幂等键的业务意义

X-API-Key 回答“你是谁”；Idempotency-Key 回答“这是不是刚才同一写操作的重试”。新增业务写接口均要求后者，建议每次新动作使用 UUID。

断网重试沿用原键和原体，返回原结果，不重复建问题或任务。改了负责人、证据、意见属于新操作，应使用新键。老请求重放也不会让旧结果重新适用于新材料；继续下一步前仍要刷新状态。

收到409先看 detail：可能是幂等键内容冲突，也可能是 epoch、要求修订、任务状态或提交版本变化。换一个键不能跳过版本核验。

## 运行完整样例

```powershell
docker compose exec -T api python scripts/business_smoke.py --base-url http://localhost:8000
```

脚本建立独立构造项目与测试账号，经过真实解析、基线、四路并发幂等登记、整改、独立复核和最终报告。最后主动发布新快照，验证旧结论失效；测试项目保留，运行报告不含明文密钥且默认不入 Git。

后续 RAG/Agent 用于辅助产生候选要求、检索响应和发现疑似问题，仍应经过这里的来源、版本与人工复核流程，不能直接改最终完成状态。
